# GitHub Issue 任務規劃

將 GitHub Issue 的需求與專案現況整理為可依序執行、可獨立驗收的任務文件。本流程僅負責任務規劃，不包含實作，不強制依賴 Work Skill。

## 1. 資料盤點

1. 依 Issue URL 確認 Repository 與 Issue 編號；僅提供編號時，透過目前專案的 Git Remote 確認 Repository，無法唯一確認時詢問使用者。
2. 完整讀取 Issue 本文、留言及狀態，依需求、工作範圍、相依關係及驗收條件讀取相關資訊。
3. 以唯讀方式盤點相關原始碼、文件、測試、設定、工作流程、工作區狀態及既有任務文件，依需求與相依關係擴大盤點範圍。
4. 依實際證據確認專案現況、需求差異及受影響範圍。

## 2. 需求釐清

1. 依盤點結果識別影響任務規劃且需要使用者決策的事項。
2. 依通用需求釐清規範進行討論，持續更新已確認需求，不將未確認事項視為已確定需求。
3. 必要需求明確後，進入任務規劃。

## 3. 任務規劃

1. 依邏輯原子性及相依關係拆分 Task，以可獨立驗收的成果作為 Task 邊界，不過度拆分。
2. 任務規劃須完整涵蓋已確認需求及 Issue 驗收條件。
3. 將任務規劃儲存至 `docs/issue-{number}/task.md`，包含 Issue 來源、已確認需求、現況與缺口，以及各 Task 的目標、工作範圍、執行順序、驗收條件及驗證方式，不限制章節結構。
4. Issue 與 Task 採分層驗收，不強制驗收條件一對一對應。使用具編號的 Markdown Checkbox，依通用驗證規範管理完成狀態。本流程不更新 Issue 的驗收狀態。

## 4. 完成條件

1. 完整涵蓋已確認需求及驗收條件，符合專案現況及適用規範。
2. Task 邊界、執行順序及相依關係合理，且具有明確、可驗證的完成條件。
3. 不存在影響任務執行的未確認需求或規範衝突。
4. 任務文件已儲存至指定路徑，完成一致性檢查後結束規劃流程。
