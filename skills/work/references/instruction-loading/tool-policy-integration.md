# Controlled Tool Policy Integration

1. [Required] Use Tooling only through Work's controlled Runtime Tool Policy channel. Discover the independent Tooling Skill through Host Skill Discovery when a concrete operation needs tool policy. Do not assume a fixed installation path, activate Tooling as an ordinary External Skill or require it for unrelated Work operations.
2. [Required] Keep Work's formal CLI Routing, `required_instruction_sources`, `source_order`, Selection Manifest, Source binding and TASK and instruction fingerprints authoritative. Tooling policy sources and their identities are runtime inputs to the current operation, not additional formal Work instruction sources. Report Tooling policy drift separately; never refresh Work formal bindings to absorb it.
3. [Required] At the Integration Gate, first require a valid Work route and current formal state. Stop the dependent operation on `REVIEW_REQUIRED`, Source drift, invalid TASK or Attempt, missing authorization or incomplete Operation Envelope. Tooling availability or a different tool cannot bypass a Work block.
4. [Required] Select Tooling policy for the actual operation, target and Host-observed tool capability. Validate its own Bootstrap, selected ancestors, applicable References, fingerprints and mandatory-rule compatibility before use. A missing or invalid required policy blocks that operation; an unrelated Work operation may continue without Tooling.
5. [Required] The Gate checks the current Work Operation Envelope and Host and user authorization against the tool's actual target, capability, Interface, side effects, recipients and policy. Tooling never enlarges an envelope or grants authorization. Preserve the distinction between a policy check and the Host's permission to invoke a tool.
6. [Required] In Task mode, tool-assisted analysis is read-only with respect to protected project state. A tool capable of writing is not authorized to write by its presence, metadata or Tooling policy. Preserve Work's existing Task routing and planning authority.
7. [Required] In Execute mode, permit changes only under a valid approved TASK, current Attempt, matching Operation Envelope and Host authorization. Check actual file and external effects against the authorized scope before and after invocation; do not infer permission from a successful tool result.
8. [Required] A Work subagent receives only the validated policy and fingerprint-bound Operation Envelope needed for its delegated operation. It cannot discover extra authority, change Work Routing or load unverified policy. If direct tool access is unavailable, the Host may coordinate or invoke the tool on its behalf under the same envelope and authorization.
9. [Required] Record tool identity, operation, policy source identities, target, actual result, affected files, relevant diff, validation and limitations in Work's existing Evidence or Attempt. Use the existing CMD `result` or OP `state` for a concise source-and-result summary, `modified_files` for actual project paths, and the existing VAL evidence and owned receipts for diff and validation proof; cite retained evidence rather than copying complete tool output. A required field that cannot be evidenced remains incomplete. Keep formal Source snapshots and closed Attempt, Correction and Recovery artifacts immutable. Do not create a parallel Tooling audit or formal selection artifact.
10. [Required] On partial success, interruption or unknown state, inspect actual Worktree and external effects before retrying or substituting a tool. Use Work's existing Attempt and Recovery authority for affected execution; do not create a Tooling recovery flow or treat an uncertain result as success.
11. [Required] Keep Tooling policy validity, target/capability binding, evidence freshness and Work authorization as separate checks. A policy update does not expand an Operation Envelope or automatically make old evidence current. Re-evaluate only affected operations when sources, target, workspace, index, analysis or session state changes.
12. [Required] Support Work-only, Tooling-only and combined installations. Work-only retains its lawful existing operations; Tooling-only needs no Work TASK. If a Work operation requires Tooling policy and it is unavailable, stop that operation and report the missing policy. Use an alternative tool only after its full policy, evidence and authorization checks pass.
