# Coordinated formal artifact revision

1. Use Revise for approved changes to an independently valid formal TASK collection, its Source provenance and Execution bindings. DiscussionSession planning and bounded saves, external skill confirmation and execution authorization keep their own formal boundaries; a checkpoint is not a formal TASK.
2. The Host gathers the complete confirmed request, decisions, requirement identity, Source/TASK/Execution routes, affected TASKs, independent selections and repository evidence before calling Work CLI. Host native delegation does not change this evidence or approval scope.
3. Keep exact original requirement bytes in immutable Source snapshots. TASK owns confirmed requirement summary, hierarchy/skill choices, main acceptance and each TASK's goal, technical decisions, steps, commands, operations and validation/acceptance criteria. Execution indexes hold derived current state; Attempt/Correction files remain immutable historical evidence.
4. Use `specification prepare → preview` to build and review the complete Source/TASK/Execution candidate set. Source replacement requires explicit review of the whole requirement, main acceptance and every TASK impact. Recheck raw Source and current collection/instruction/skill proofs before binding one approval to the exact preview fingerprint.
5. After approval, `specification apply` publishes only that candidate set. Read-only `specification verify` checks the installed transaction; `specification recover` resumes the same approved journal after interruption. Preserve original snapshots, specification history, Attempt/Correction files and current evidence of partial writes. Do not handwrite formal JSON, roll back history or claim filesystem atomicity across files.
6. For execution-deviation reconciliation, select actual immutable closed Attempt evidence and explicit retain-only or semantic migration decisions. Use reconciliation prepare/preview/apply/recover; nested migration shares the complete approval and publication boundary. Recompute affected TASK/downstream acceptance state without reviving invalidated evidence.
7. A separately authorized Session update binds its expected revision and content fingerprint; it does not reuse formal publication approval. Reuse approval only for the identical concrete previews already authorized. The Host resolves outstanding requirement or technical choices with the user; native delegation grants no write permission.
8. The Host resumes its workflow from committed formal state, reloads and revalidates changed sources, and repeats Execute preflight before execution. A successful revision grants no implementation or new Attempt authorization. Drift or transaction failure preserves the workspace and stops dependent operations; recovery requires authorization for the owning transaction's exact candidates.
