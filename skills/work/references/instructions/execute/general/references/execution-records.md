# Execution records

## Project file publication boundary

1. [Required] For a Task declaring file changes, call `execute file-apply` directly with the complete current `changes` and `expected_before` from the read. The baseline must cover every written path and move source and destination, using SHA-256 of raw bytes or null for absence. Do not refresh it without rereading and integrating content. Reuse current Attempt scope authorization; manual staging and separate publication approval are unnecessary. `file-prepare` is an optional preview. Derive every final path from the same initial file tree; see [Complete file publication and restoration](../../../../workflows/execute/publish-project-files.md). Git status cannot replace complete content and path-identity evidence.
2. [Required] Run argv CMD under Host-provided environment and limits. Work does not create AppContainer or Seatbelt isolation or take over tools and artifacts; retain required lifecycle handling for ordinary Windows Jobs and macOS process groups. Linux and shell mode are unsupported. Do not bypass Host rejection. Automated VAL checks structured conditions and real owned CMD receipts. External OP retains separate authorization and side-effect handling; recoverable local files do not imply cross-system atomicity.
3. [Required] An Attempt may repeatedly complete changes, tests and fixes. Order history by prior transaction identity and preserve current before-state each time; never restore over an earlier successful outcome. Explicitly confirm and persist a new actual baseline for user changes between operations, bound to the preceding transaction and fingerprints of complete bytes, metadata, existence and native identity, plus confirmation evidence. Unconfirmed or post-confirmation drift still blocks. If original scope explicitly has `rollback_on_write_failure: true`, the current write is known to have failed, and whole-set state and identity are unchanged, revert only this write and record failed-and-restored. Do not revert after a complete write followed by a test failure. Preserve evidence and block after crash, unknown state, foreign change or failed restoration. Explicit Recovery needs new authorization and cannot retroactively authorize an old transaction.
4. [Required] Completion and close Recovery check complete ordered history, actual current versions and all required acceptance. A historical generation CMD cannot stand in for acceptance of a new version. Every non-skipped VAL stores a program-verified file version; changes require revalidation. Restored history without a successful publication cannot complete. If a later failed write was restored after an earlier successful one, preserve the earlier result and require revalidation of the new version. Reject the whole set before modifying formal targets if metadata or ACL cannot be fully preserved and restored; do not claim unknown existing metadata is complete.

## 1. Paths, TASKs and fingerprints

1. [Required] Command receipts' `execution.input_files` stores content fingerprints for concrete project_state files declared by Task and actual task_output paths. A directory stores only a scope type, not recursive content evidence. VAL `file_version` binds modification history and currently declared inputs; input drift prevents old acceptance from completing the Task. Preserve original command and validation records, never rewrite history or automatically rerun commands with unknown results, and do not expand this into build artifacts, caches or toolchain management.

1. [Required] Execute uses only the requirement ID, explicit TASK and Execution paths, and Task-owned fixed Source binding established by the formal TASK or complete handoff. Apply the shared instruction-loading's complete requirement-artifact path-safety checks before each read or write. Do not infer, replace or redecide them from one path.
2. [Required] Validate `task_collection_sha256`, `task_index_sha256` and target `task_item_sha256` separately. Calculate all under the shared loader and canonical fingerprint rules; define no alternate normalization.
3. [Required] Recalculate the target TASK's `TASK-INSTRUCTIONS-SHA-256` from its formal `instruction_selection` and the shared canonical instruction fingerprint, with shared instruction-loading fixed as the first source. Also check the index's document-level union value. A source change for an unrelated TASK must not block the target.
4. [Required] `EXECUTE-INSTRUCTIONS-SHA-256` covers only Work Execute instructions and applicable References. Bind External Skill identity separately through the target TASK's `skill_id` and `execute_skill_selection_sha256`; do not mix it into the Work hierarchy fingerprint.
5. [Required] Omit an instruction source only after confirming a raw-byte duplicate. Do not deduplicate by lexical sort, equal normalized content or equal parent instructions.
6. [Required] Before creating an Attempt, use Work CLI `execute preflight` to revalidate the canonical TASK, canonical index, specified TASK, direct dependencies, Task instruction fingerprints, existing lock, current Execute instruction fingerprints, input sources and specified TASK file lifecycles. Pass confirmed full INPUT IDs for `user_provided` or `external` inputs, never values. Success has `work-execute-preflight` and `eligibility: passed` and writes nothing.
7. [Required] After preflight, run `execute worktree` with the same input to list staged, unstaged and untracked paths read-only via Git porcelain v1 `-z`, excluding only the current Execution directory. `work-execute-worktree` path classes aid review but do not prove ownership. Do not create an Attempt for an unexplained difference.

## 2. Index

1. [Required] The Execution index is `index.json` in the Execution directory, distinct from the formal TASK index and DiscussionSession. Manifests and payloads for the seven transaction types live at `outputs/work/runtime/staging/<requirement-id>/<operation>/<full-transaction-sha256>/`, never at the Execution root. Preserve old `.work-*.tmp` evidence and block normal writers. The index stores primary `acceptance_results`, TASK-row acceptance progress, TASK/Attempt/VAL/retry record IDs for each evidence item, Task item and instruction fingerprints, TASK spec, collection and formal-index fingerprints, per-TASK item fingerprints, Task-owned `hierarchy_selection_sha256` and `skill_selection_sha256`, document-level Task instructions SHA, optional audit and lock, overall state and TASK rows; it does not store full Skill text.
2. [Required] A TASK row always has TASK ID, state, `skill_id` and that TASK's instructions SHA. Add latest Attempt, Correction or state reason only when present.
3. [Required] TASK states are only pending, in_progress, pending_retry, blocked, completed and cancelled. Overall state is cancelled when all are cancelled; otherwise ignore cancelled TASKs when determining pending, completed, blocked or in_progress precisely.
4. [Required] The initial Attempt execution lock has `kind: execution`, `task_id`, `attempt_id` and `execute_instructions_sha256`. A later record transaction adds `record_id` only before CMD, OP or VAL execution. Specification and execution locks are mutually exclusive; while any execution lock exists, create no other Attempt, Correction or specification lock. Recovery and close interpret the operation with the original Execute hash in the lock.
5. [Required] Overall state is cancelled if every TASK is cancelled. Otherwise ignore cancelled TASKs: it is pending if all remaining TASKs are pending; completed if all required TASKs are completed; blocked if none is in progress or executable and every incomplete item has a direct or dependency blocker; otherwise in_progress. A cancelled TASK is neither completion nor acceptance evidence.
6. [Required] Do not execute under a specification lock; Execute cannot release it. An Attempt lock lasts from before Attempt creation until close records and index are synchronized. A Correction lock lasts until Correction, TASK, downstream and index are all synchronized.
7. [Required] For required and optional Execution index fields, canonical key order, constraints, nested contract references or current valid examples, run `<work-cli> contract describe work-execution-index` and follow its registry response. Do not duplicate or maintain a full JSON structure in instructions.

## 3. Attempt creation and content

1. [Required] An Attempt lives at `<execution-dir>/<TASK-ID>/<ATTEMPT-ID>/attempt.json`; each TASK increments from `ATTEMPT-001`. A TASK has at most one in-progress Attempt. Create its directory and file only after the lock write succeeds. Support only this directory structure; report legacy flat Attempt or Correction JSON under a TASK directory as an error without moving it automatically.
2. [Required] A new Attempt uses canonical `work-attempt` and stores in order schema, Attempt ID, TASK spec, TASK ID, `skill_id`, state, TASK SHA, Task instructions SHA, Execute instructions SHA, `hierarchy_selection_sha256`, `execute_skill_selection_sha256`, complete authorization manifest and fingerprint, start time, primary and TASK `acceptance_results`, optional continuation data and records.
3. [Required] Append execution records in actual order. Use the original ID first and suffix repeated executions `#1`, `#2` in order. A CMD records exit code and a one-line key result or minimal error; an OP records success or failure and required external state without the full response; a VAL records pass or failure and minimal evidence or sufficient preceding IDs.
4. [Required] When files change or output is carried forward, maintain cumulative modified files for this Attempt as the union of valid carried and current paths, without diffs or file hashes.
5. [Required] At close add end time, final state, applicable type and concrete reason. Time uses `YYYY-MM-DDTHH:mm±HH:mm` with offset; closed content is immutable.
6. [Required] If TASK-SPEC or TASK SHA changes, close the old Attempt against its original baseline before creating the next under the new specification. Once an external blocker clears, new authorization may directly create an in-progress Attempt without a separate pending_retry transition.
7. [Required] For required and optional Attempt fields, canonical key order, constraints, nested contract references or current valid examples, run `<work-cli> contract describe work-attempt` and follow its registry response. Do not duplicate or maintain a full JSON structure in instructions.

## 4. States and results

1. [Required] `status` is only `in_progress`, `completed`, `stopped` or `blocked`. A stopped `final_type` is only `specification_defect`, `instructions_changed`, `validation_failed`, `unexpected_change`, `external_operation_failed`, `user_stopped` or `other`; a blocked one is only `environment`, `external_service`, `permission`, `required_input` or `other`.
2. [Required] Map Attempt to TASK as follows: in_progress to in_progress; completed to completed; ordinary stopped to pending_retry; specification defect, Task instruction change or external operation failure to blocked; blocked to blocked. If an in-progress Attempt stops because Execute instructions changed, keep the TASK blocked until impact is confirmed. After confirming it can rerun under the current TASK, move to pending_retry and use new instructions only in a newly authorized Attempt.
3. [Required] Record external or multistep outcomes as `Overall result: Complete success / Partial success / Failure / Uncertain result` and, as applicable, `Effective`, `Not effective` and `Unknown`. Partial success and uncertain result cannot mark an Attempt completed. Map each OP's success, failure or unknown outcome to the corresponding detail, and keep the overall result consistent with OP records.
4. [Required] New Attempts and the active Execution index must pass the complete current contract. Preserve original bytes of existing closed Attempts as historical evidence; do not rewrite missing fields or assume they pass the current validator. Handle incompatible active artifacts through approved Migration.
5. [Required] Current instructions and fingerprints constrain only future new Attempts or resumption decisions. An instruction update does not invalidate evidence valid in closed history at the time unless a separate confirmed decision requires review.
6. [Required] Completion needs currently valid passed evidence for original and accepted supplemental VALs. An approved non-blocking `skip_record` only closes its reservation legally; it cannot satisfy required acceptance or count as a pass or success. Do not mark unrun work without approved evidence, unknown exit codes, compile-only checks without acceptance, zero tests or subjective guesses as passed.
7. [Required] Only Task/Revise sets cancelled. Execute cannot cancel, uncancel or reactivate a TASK. After all required non-cancelled TASKs complete, still check tool-aggregated primary acceptance and actual Attempt evidence; TASK state alone does not establish primary acceptance. Do not reread every Attempt or create `completion.md`. All-cancelled means only that no execution is currently needed, not that acceptance completed. Primary and TASK acceptance completion accepts only actual passed VAL evidence under current mapping; carried and skipped records satisfy permitted close coverage but do not create acceptance completion evidence for the new Attempt.

## 5. Fixed record format

1. [Required] The index is one canonical plain JSON object. Order `tasks` as in the TASK document and fields exactly as the Work CLI renderer does. Include optional fields only when present, with no extra text lines or placeholders.
2. [Required] Append discriminated `records`: CMD has `id`, `kind: command`, optional `correction`, integer `exit_code` and one-line `result`; OP has `id`, `kind: operation`, `outcome: success|failure|unknown` and minimal `state`; VAL has `id`, `kind: validation`, `outcome: passed|failed` and minimal `evidence`, plus producer-owned `source`, `file_version` and provenance proof. An approved non-blocking `skip_record` instead stores the original `id` and `kind`, `status: skipped`, exact `reason` and `deviation_id`; it cannot fabricate normal result fields or count as OP success. Cumulative files use normalized project-relative `modified_files`, with no diff or hashes. CMD `correction` stores canonical `original_command`, `actual_command`, `reason` and `authorization_evidence`; both commands retain the same `argv|shell` mode and must differ.
3. [Required] Add `ended_at` for `completed`; add `final_type`, `reason`, then `ended_at` for `stopped` or `blocked`. A closed Attempt with OPs includes `overall_result`, whose `effective`, `not_effective` and `unknown` list corresponding OP IDs exactly. `partial_success`, `failure` and `uncertain_result` cannot accompany `completed`.
4. [Required] A continuing Attempt uses `continued_from`; optional `carried_records` stores `source_attempt_id`, `record_id` and minimal currently valid `evidence` in original TASK ID order. Omit IDs not carried; never replace source, ID or validity evidence with a summary. Reexecuting a carried ID continues `#1`, `#2` numbering.
   Only a trusted writer creates automated VAL `validation_evidence`, preserving immediate source, final owner Attempt SHA and actual original VAL record; callers cannot provide it. Current authorization must cover the VAL and criterion mapping. Recheck current conditions, engine, source bytes and complete CMD receipts before carrying acceptance. Acceptance evidence `attempt_id` identifies the receiving current scope; optional `source_attempt_id` identifies the real VAL owner. Do not invent a VAL record, rerun CMD or change history. Current CMD retry or skip, or condition or evidence drift, invalidates old VAL carryover and requires a formal new VAL for the current result. Publication and Recovery recheck the same frozen provenance; unknown cannot pass.
5. [Required] Before any Attempt write, plain JSON must pass Work CLI `attempt validate --input-file "<request-path>"`. `--verbose attempt render --input-file "<request-path>"` returns canonical field order. For an existing file, `attempt validate --path "<attempt-path>"` checks plain JSON, the `attempt.json` filename, Attempt parent directory, TASK grandparent and canonical bytes. These commands are read-only and create no Attempt, lock or index state.
6. [Required] A Correction lives at `<execution-dir>/<TASK-ID>/<ATTEMPT-ID>/corrections/<CORRECTION-ID>.json`; create `corrections/` with the first Correction. Increment IDs within each Attempt and validate directory and target Attempt identity. A Correction is canonical plain-JSON `work-correction` with only registry-defined English fields and order, no extra summaries or synonyms. `correction validate` checks plain JSON or an existing file; `--verbose correction render` returns canonical JSON in response.data.
7. [Required] For required and optional Correction fields, canonical key order, constraints, nested contract references or current valid examples, run `<work-cli> contract describe work-correction` and follow its registry response. Do not duplicate or maintain a full JSON structure in instructions.
8. [Required] Create a Correction with plain-JSON `work-correction-create-request` and `execute correction-create --input-file "<request-path>"`. `invalidates_completion` is a required Boolean transaction decision, not part of immutable Correction. Work CLI derives the next ID, current offset-minute time and original Attempt fingerprints, then atomically replaces the Correction lock, exclusively creates the canonical Correction and replaces the final index in order. When completion must be invalidated, move only the target and completed downstream TASKs to `pending_retry`; cancelled TASKs remain unchanged. Reset affected acceptance to pending and remove current completion evidence without changing original Attempt or Correction history.

## 6. Attempt start transaction

1. [Required] `execute worktree` derives the `work-execute-worktree-snapshot` SHA-256 from unclassified Git status and the Execution-directory exclusion. Work CLI excludes process locks and temporary records wholly within `outputs/work/runtime/` so owner creation does not change the reviewed snapshot. Still review renames crossing the runtime boundary and similarly named paths. The user must review the complete worktree result; the hash binds reviewed state but does not replace explicit authorization.
2. [Required] Create an Attempt with plain-JSON `work-attempt-start-request` and `execute attempt-start --input-file "<request-path>"`. The request includes complete `work-attempt-authorization`, listing approved commands, validations, mutable files, working directories, external operations, complete execution-deviation actions, fixed reask conditions and authorization evidence field by field; wildcards are invalid. Work CLI checks that it exactly matches or narrows the current TASK, produces an authorization fingerprint and derives the next Attempt ID, current offset-minute time, TASK identity and three fingerprints. After rechecking preflight and snapshot, it installs the execution lock, exclusively creates the canonical Attempt and synchronizes `in_progress` and `latest_attempt` in order, retaining the lock throughout and executing no CMD, OP or VAL.
3. [Required] A `pending_retry` request supplies the latest source Attempt and each carried record ID with currently valid evidence; `pending` cannot include continuation. The source must be the latest closed Attempt for the same TASK, carried IDs must exist, and cumulative modified files are copied.
4. [Required] On interrupted start, retain lock, Attempt and complete staging manifest and payload inventory; return `recovery_required` with the precise phase. Do not automatically roll back, delete, unlock or continue.
5. [Required] Before each formal CMD, OP or VAL, confirm its base ID, action and side effects are covered by current Attempt authorization, then call `execute record-begin`; do not reask per covered record. Work CLI validates current TASK, Attempt, index lock and Task/Execute fingerprints, derives the original ID or next `#n` from carried and existing records, then atomically replaces the index to add actual `record_id` to the lock. Success returns `work-record-begin` with `lock_status: record_reserved` without executing or appending that record.
6. [Required] Stop record-begin for an existing `record_id`, changed instructions, a nonformal ID or transaction conflict. On interrupted write, retain the original lock and the same `record-begin` staging manifest and payload, returning `recovery_required`. Do not retry automatically, execute the record, remove temporary files or release the lock.
7. [Required] For an equivalent correction to a reserved CMD, first confirm unchanged semantics and side effects under the main instruction's execution-deviation boundary; obtain a user decision if original Attempt authorization did not precisely cover the replacement. Before execution, call `execute command-correction --input-file "<request-path>"` with plain-JSON `work-command-correction-request` containing only user-approved `actual_command` and semantic reason. The tool derives record identity and original command from active lock, formal TASK, Attempt and approved deviation, and only atomically replaces the index to store `command_correction`; it neither executes nor judges semantic equivalence. Record only one correction per record.
8. [Required] Execute the actual command only after command-correction returns `work-command-correction`, `correction_status: recorded` and `lock_status: record_reserved`. On interruption, retain the lock and same `command-correction` staging manifest and payload and return `recovery_required`. Do not execute, resend, delete, roll back or unlock.
9. [Required] After a reserved record finishes, call `execute record-finish --input-file "<request-path>"` with plain-JSON `work-record-finish-request`. Do not reask merely to record an authorized known result; stop for a decision if the result is uncertain or side effects exceed authorization. Do not fill `record.id`, `record.kind` or correction manually. The CLI derives the actual record instance from active lock and valid TASK. A command supplies `exit_code` and `result` but no request correction; an operation supplies `outcome` and `state`; validation supplies `outcome` and actual program evidence, AI `review` or the named user's actual `confirmation` document according to formal kind. The producer preserves source, version and frozen proof; the caller cannot provide them. An approved non-blocking `skip_record` supplies `status: skipped`, approved `reason` and matching `deviation_id`, without normal results, changed files or extra authorization evidence. Pass normalized `modified_files` separately for ordinary execution that changed files.
10. [Required] Record-finish first incorporates the lock's command correction into CMD, then atomically replaces the canonical Attempt, appending the record and updating cumulative changed files and OP overall result. It derives primary and TASK `acceptance_results` from actual VAL records and current TASK mapping and synchronizes the index; another atomic index replacement removes `record_id` and `command_correction` from the lock while retaining the Attempt lock. The tool does not execute the record. On interruption, retain written content, lock and the same `record-finish` staging manifest and payload and return `recovery_required`; do not resend the result, start another record, roll back, delete or unlock.
11. [Required] Close an Attempt with plain-JSON `work-attempt-close-request` and `execute attempt-close --input-file "<request-path>"`. `completed` supplies no final details and requires the latest current or carried result of every formal VAL to pass. `stopped` and `blocked` supply an allowed `final_type` and concrete `reason`. Work CLI generates end time; the request cannot set it.
12. [Required] Attempt-close confirms no reserved `record_id` or `command_correction`, atomically replaces the canonical closed Attempt, then atomically replaces the index to synchronize TASK and overall states and remove the execution lock. Do not reask when all authorized records succeeded and reviewed normal close conditions hold. Obtain a new decision for stop, block, uncertain result, unreviewed deviation or other abnormal close. Map `completed` to completed, ordinary `stopped` to pending_retry, specification defect, instruction change or external operation failure to blocked, and `blocked` to blocked. On stop or block, the tool invalidates affected acceptance while retaining original records; normal completion retains actual acceptance evidence. The tool executes no record.
13. [Required] On interruption at any attempt-close step, retain written Attempt, original lock and the same `attempt-close` staging manifest and payload and return `recovery_required`. Do not resend, roll back, delete or manually unlock. Return `work-attempt-close` and `lock_status: released` only when Attempt and index are fully synchronized.
14. [Required] CMD record-finish checks exit code and Task/Attempt/Record identities against real owned receipts. Formal VAL kind determines evidence source, never the actor name: automated checks complete real output and reports of the latest CMD, or actual zero exit codes for all command_ids when verification is unspecified; explicit conditions may require nonzero, and unknown cannot pass any or not. ai_review preserves review by the named reviewer with concrete references and reasons, checking file hashes, owned CMD receipts or complete before/after publication differences; a bare passed claim is invalid. manual preserves the named confirmer's actual user message or document and source reference, bound exactly to Task, Attempt, VAL, retry, file_version and outcome from record-begin; AI cannot fabricate user confirmation. CLI freezes original bytes and proof but does not claim cryptographic identity authentication against other processes under the same OS user. Complete or release downstream only when every required condition has complete current-version evidence from the correct source. Any new file change invalidates old acceptance. Host rejection, unrun, truncated, missing or unknown results remain incomplete; AI conclusions cannot hide program failures.

Normal records reuse the active Attempt authorization. Supply new authorization
evidence only when beginning a retry or recording a failed or unknown result.
The reserved-record lock preserves retry evidence for downstream receipts and is
released only after the record is finished or explicitly recovered.

## Continuation across flows

1. [Required] Preserve a CMD's real historical exit code once it has a complete finished receipt, even if declared inputs drift; its old result cannot serve a current VAL. Preserve current user content, end an invalid VAL reservation with an approved skip_record, then run new CMD and VAL under actual authorization. Do not revert to old content, delete the lock, rewrite history or rerun unknown results. Historical integrity of a carried old VAL cannot block legitimate new evidence, but close still rechecks current validity.
2. [Required] Link complete create or move output of a normally stopped Attempt through `continued_from` and the preserved transaction chain. A new Attempt needs separate Execute authorization and checks current bytes, metadata and path identity; no reset or repeated publication is required.
3. [Required] Check Migration sources against the real approved journal, original evidence, candidate, publication marker and current Task. Obtain Execute authorization separately; do not fabricate Discussion or Snapshot.
4. [Required] For a simple added file, use an idle Attempt's add_files deviation. First record exact paths, reason and change type and check all cross-Task dependencies. Original scope must include additional_files; this cannot expand modules or explicit file limits. Follow the existing Attempt authorization-boundary workflow.
