# Execution recovery

## 1. Locks and write protection

1. [Required] The index's persistent business lock stores coordination state for Attempt, record and Correction. It does not expire automatically and is released only after the matching operation fully synchronizes or a separately authorized recovery. Handle the exclusive process owner under Item 5.
2. [Required] Before writing, derive complete staged content and its hash solely from approved local limited differences, using target encoding and newlines. Replace only after confirming source files still match precondition evidence. Do not reformat, reorder or reconstruct unchanged content. Immediately strict-decode the write and inspect the limited diff.
3. [Required] After partial publication of a multi-file operation or interrupted Attempt or index synchronization, do not automatically roll back, delete or open another Attempt. Preserve current state, business lock and staging evidence; summarize again and obtain recovery authorization before proceeding. A controlled exit releases only this process owner.
4. [Required] TASK fixes encoding, BOM and newlines for new text files. Otherwise determine the same-type convention in the project read-only. If it cannot be confirmed and non-ASCII or acceptance would be affected, treat this as a specification defect. Do not rely on shell default encoding.
5. [Required] Work CLI's exclusive process lock is `outputs/work/runtime/locks/<requirement-id>/execution.lock`, determined by the validated TASK requirement and canonical project root; a custom Execution path does not change lock identity. Exclusive creation stores a unique owner. On success or controlled error, release explicitly and delete only the matching owner's lock file, never the business index lock, staging or formal evidence. A kill or abort, unknown owner or old writer-lock residue remains blocking until all writers stop and an independent offline review completes. Do not reclaim based on age, timeout, PID or an old OS lock no longer being held. This process lock and the persistent Execution business lock have separate lifecycles.

## 2. Recovery and continuation

1. [Required] Before recovery, check read-only the lock, formal TASK collection, fixed Source original bytes and binding, both instruction fingerprints, Execution index, target Attempt or Correction, worktree and external state. The original Execute-instruction baseline for Attempt or Correction is the lock's `EXECUTE-INSTRUCTIONS-SHA-256`. Retain the lock and refer to the user if any item cannot be explained uniquely.
2. [Required] If the Attempt named by a lock is absent, recreate that same Attempt only with authorization, only if its ID is still next, the TASK is executable and no unknown side effect exists. Do not choose another ID.
3. [Required] For an in-progress Attempt with unchanged current Execute-instruction hash, resume only the same TASK proven by records and current state; completed CMD, OP and VAL may be carried only while still valid. With insufficient evidence or unknown results, preserve receipts, lock and complete transaction evidence and obtain a decision; never rerun a command automatically to guess its result. A separately authorized retry uses the existing new-record-ID flow. If the hash changed, do not resume directly: obtain authorization under general Execute instructions, stop the old Attempt under the original hash in the lock, synchronize and unlock, confirm impact, then carry still-valid evidence into a new Attempt.
4. [Required] If the Attempt is closed but the index is not synchronized, do not modify the Attempt. With authorization, synchronize only its final state and release the matching lock.
5. [Required] Complete missing or partially new attempt-start files for the same Attempt only with separate authorization and only when the complete transaction manifest, originally approved request, fixed before and after bytes and unique publication order can all be verified. Use the start time in the manifest, not recovery time or model inference. Preserve state and stop for a missing manifest, conflict or unknown content.
6. [Required] For conflicting existing content, multiple in-progress Attempts, unexplained records or side effects, or missing values that cannot be reconstructed uniquely, list locks, paths, confirmed fields, conflicts and expected skeleton. Let the user resolve them, then recheck read-only. Do not modify, delete or move conflicting records or release the lock.
7. [Required] If the index points to the sole in-progress Attempt but lacks an execution lock, first check TASK-SPEC, fingerprints and worktree read-only, then recreate the matching lock with authorization. Resume no CMD, OP or VAL before the lock is restored.
8. [Required] Continuation may reference only the latest closed Attempt of the same TASK, without skipping or cycling. Copy its verified cumulative changed files. Omit reexecution only for CMD, OP and VAL that records and current state jointly prove remain valid for the current TASK and have not been invalidated by a specification change.
9. [Required] Seven Execution transaction types live at `outputs/work/runtime/staging/<requirement-id>/<operation>/<full-transaction-sha256>/`. Complete `transaction.json` fixes canonical root, requirement, Execution path, approval, business IDs, before and after bytes, payload inventory and publication progress. After an interrupted attempt-start, review all this evidence first, then run `execute recover-attempt-start --input-file "<request-path>"` with the original `work-attempt-start-request` and explicit TASK and Execution paths and IDs. Advance only the unique canonical targets of the same transaction; do not execute CMD, OP or VAL.
10. [Required] If `record-begin`, `command-correction`, `record-finish` or `deviation-record` staging exists, preserve complete manifest, payload and formal state and stop ordinary writes. Normal commands cannot recover automatically. Review the lock's `record_id` and `command_correction`, Attempt records and deviations, and frozen targets together.
11. [Required] If `attempt-close` staging exists, an Attempt is closed but its index unsynchronized, or formal targets finished but cleanup stopped, preserve the closed Attempt, business lock and remaining runtime evidence. After separate authorization, complete only synchronization and cleanup in fixed before-to-after order; do not rewrite the finished close result.
12. [Required] For general transaction recovery, first use `execute recovery-prepare` to produce `work-execution-recovery-request`; after review, call `execute recover --input-file "<request-path>"` with the original plain-JSON `data.request`. Transaction kinds are `record_begin|command_correction|record_finish|deviation_record|attempt_close|correction|command_isolation`. The request requires the target Attempt, project-relative `transaction_dir`, complete sorted actual `transaction_files` within it and `transaction_evidence_sha256`. Inventory includes `transaction.json` and existing control tmp files and payloads; missing or verifiable partial states also enter the evidence digest. Reject old `.work-*.tmp` requests. Do not infer requirement from Execution basename or reconstruct old paths.
13. [Required] `execute recover` rechecks current inventory and SHA-size digest, formal TASK and Source, canonical artifacts, original lock, complete manifest and unique domain target, then advances in original transaction order. A failed result still needs new authorization evidence. Formal files accept only a fixed before/after graph; partial new artifacts or prepared payloads can complete a matching prefix only with complete frozen proof. Reject and preserve bytes for unknown formal state, foreign entry, missing manifest, mixed transactions or evidence changed after approval.
14. [Required] Progress uses `transaction.json.tmp` in the same directory. Only explicit recover may complete a prefix of the next monotonic state when complete proof matches the actual formal graph. Enter published_verified and cleaning only after strict reread of all formal targets. Remove only listed runtime payloads for this transaction, then the manifest last; failed cleanup retains complete reentrant identity evidence. A controlled error returns `recovery_required`, transaction directory and verifiable progress and releases only the matching process owner. Never touch formal receipts, history or unknown entries or clean with a whole-directory or glob deletion.
15. [Required] `execute recovery-prepare --input-file "<preparation-path>"` assembles a request read-only. It takes `work-execution-recovery-prepare-request`, confirmed transaction and attempt_id, and explicit TASK and Execution paths, TASK ID and roots. It inventories complete current staging, formal sources and SHA-size, then produces a request with evidence digest. It neither writes nor obtains recovery authorization nor replaces recover's unique domain-target validation. If evidence bytes, size, set, missing or partial state changes, the old request expires and needs a new preview and approval. The user still checks external side effects.
16. [Required] Forward Recovery of record-finish or completed attempt-close rechecks real owned CMD receipts, source, proof and current file version for each of the three acceptance kinds, and complete publication history; never publish success for invalid or unknown evidence. Preserve started and finished state, original output and reports for interrupted commands, without inventing exit codes or rerunning. Preserve files after a complete write followed by test failure; fix and revalidate within existing authorization. Restore only the current known failed write when original authorization permits and whole-set before-state and actual identity are unique. Otherwise use `file-recovery-prepare → file-restore` for explicit recovery authorization, preserving earlier successes and confirmed user content.
17. [Required] Old AppContainer and Seatbelt settings, native profiles, old locks and partial transactions are offline-review evidence only. Current Work provides no command_isolation cleanup or old sandbox fallback. Do not delete unknown native resources, infer process termination, or rewrite or rerun historical CMDs. The deployment owner confirms side effects and handling in the original environment under existing Migration diagnostics.

## 3. Correction

1. [Required] Correction fixes an erroneous fact in a closed record or index only; it does not change the TASK, implementation or original Attempt. Use the next `<ATTEMPT-ID>-CORRECTION-nnn` each time with separate authorization and a Correction execution lock preserving the original `EXECUTE-INSTRUCTIONS-SHA-256`.
2. [Required] Canonical `work-correction` stores creation time, target, original Attempt's Task and Execute fingerprints, field, correct value and reason. It is immutable after formal artifact publication. Keep `invalidates_completion` and affected TASK IDs in fixed evidence in the business lock and transaction manifest, not in immutable Correction.
3. [Required] On interrupted Correction, use recovery-prepare's `transaction: correction` request, preserving the same target Attempt, complete `transaction_dir`, actual inventory and evidence digest, then approve recover separately. Correction ID, canonical artifact, original fingerprints, lock affected plan and final index bytes must match exactly. Never overwrite, delete or unlock unknown or conflicting content.
4. [Required] When a lock points to an unpublished Correction, create it only if the original approved canonical artifact, ID, lock and final-index targets preserved in a complete manifest remain uniquely valid. If the existing artifact matches exactly, finish only later index and cleanup steps without rewriting immutable Correction. Stop when complete manifest or frozen bytes are missing; do not infer values.
5. [Required] When Correction invalidates completion, set target and completed downstream TASKs to pending_retry and reset affected acceptance results. Preserve original Attempt and Correction records without writeback. Record a state-difference reason only when TASK state conflicts with latest Attempt result. Cancelled TASKs remain cancelled and cannot be reactivated by Correction.
