# Java JPA task planning

Instruction boundary: This layer only fixes contracts specific to affected JPA/Hibernate flows. Inherit common relational-data and Java requirements from parents without repeating them here.

1. [Required] The TASK must confirm the target module's actual JPA provider, applicable Spring Data JPA/Hibernate, Persistence namespace, Repository abstraction, annotation processing and affected Entities/queries. Do not migrate between `javax.persistence` and `jakarta.persistence` independently.
2. [Default] Fix a compatible annotation processor, generated-source directory and compilation validation only when affected Criteria/Specification code or an existing build contract actually needs a static metamodel. Do not add a processor when it is inapplicable.
3. [Required] When a static metamodel applies, align processor coordinates and version with official information and the actual Hibernate core/BOM. Fix Maven/Gradle declaration placement, annotation processing, generated-source directory, compilation integration and cleanup behavior. VAL must prove the processor ran and target `*_` classes were generated and compiled. Do not replace generated attribute references in Criteria/Specification with string paths.
4. [Required] Fix primary keys, generation strategies, access type, Entity/table/column names, nullability, length, precision/scale, uniqueness, defaults, enums, date/time, identifier immutability, schema and equality for Entity mappings from actual fields. Do not edit generated files manually.
5. [Default] Map enums explicitly as strings or with a confirmed converter, not by ordinal. For composite keys, fix `@EmbeddedId` or `@IdClass`, value equality and query validation. Fix proxy, transient and persisted behavior for Entity equality; do not rely only on mutable fields or database-generated IDs.
6. [Required] For every affected relationship, fix cardinality, owning side, `mappedBy`/join column, nullability, collection type, bidirectional synchronization, fetch plan, cascade, `orphanRemoval` and lifecycle tests from the actual lifecycle. Use the smallest cascade set; use `orphanRemoval` only for children privately owned by the parent. Do not assume `CascadeType.ALL`.
7. [Default] Obtain query-needed relationships through per-query fetch joins, Entity Graphs, projections, batch fetch, subselects or an existing method. Do not switch globally to EAGER to avoid N+1. Fix risk-based SQL/query-count limits for queries that may load relationships. For large data, also fix projection, pagination/scrolling, indexes, memory limits and representative-data validation.
8. [Required] Follow the project's existing architecture for Repository and transaction responsibilities; do not assume four layers. Use a custom Repository/`EntityManager` only when existing abstractions cannot express the requirement, and fix reason, boundary and tests.
9. [Required] Follow existing derived queries for simple conditions, use Specification/Criteria for composed conditions by convention, and explicit JPQL/HQL for complex fixed queries. Bind all values as parameters; accept dynamic fields and sorts only from backend allowlists. Use native queries only when standard queries cannot express the requirement correctly or a confirmed performance need exists; fix dialect, SQL, result mapping, count query, constraints and validation.
10. [Required] Fix uniqueness, not-found behavior and the `Optional`/exception contract for single-record queries. For pagination, fix `Page`/`Slice`/`List`/scroll, per-page limit, overflow, total count and stable ordering with a unique tie-breaker. When pagination combines with collection fetch joins, native queries or complex projections, fix and test a correct data and count approach.
11. [Required] Put transaction boundaries around complete business units of work; prefer `readOnly = true` for reads and fix rollback for writes. Fix reasons and tests for nondefault propagation, isolation, timeout or rollback. Keep lazy loading and DTO conversion inside the fixed boundary; do not rely on Open Session in View.
12. [Default] Use `@Version` only when concurrent updates are possible and optimistic locking fits the conflict contract. Do not add it when unnecessary; fix an alternative when consistency protection is needed. Fix consistency behavior when merging detached Entities. For pessimistic locking, separately fix lock mode, ordering, timeout, deadlock/retry, transaction boundary and validation.
13. [Required] For update, delete and Bulk DML, fix conditions, target scope, expected affected row count, `@Modifying`, flush/clear and stale persistence-context state. Do not unintentionally bypass versions, listeners, auditing, soft deletion, tenants or data permissions. Full-table operations are prohibited by default.
14. [Required] For batching, fix data volume, JDBC batch settings, key-strategy compatibility, batch size, ordering, periodic flush/clear, transaction size, memory limit and failure/rollback/partial-success behavior. Do not claim batching from `saveAll` alone or substitute uncontrolled per-row writes.
15. [Required] When auditing, Entity listeners, soft deletion, tenancy or data permissions are affected, fix creator/updater, time and principal sources, query conditions, bulk/native behavior and tests. Entities must not read Controller, HTTP Session or security-framework context directly.
16. [Required] In formal environments, do not replace migrations with unapproved `ddl-auto=create`, `create-drop` or `update`. Validate Entities, constraints, indexes, foreign keys and sequences against the approved schema source and migration.
17. [Required] VAL covers actual impacts on mappings, constraints, Repository, null/uniqueness, relationship ownership, cascade/orphan behavior, fetch/query count, pagination/count, transactions/rollback, lock conflicts, bulk persistence context, batches, auditing/soft deletion/tenancy and migration. Use `@DataJpaTest` only when present and applicable. Authorize database connections under the relational-data Reference and disclose unverified risks.
18. [Required] When departing from an applicable safe default, the TASK must fix the reason, data-volume and lifecycle boundaries, alternative and direct validation. Do not proactively refactor untouched JPA code merely to apply instructions.
