# Apply one Attempt authorization boundary


1. Before starting an Attempt, present the goal, project/modules, modification types, risks, validation and covered Task set. A current authorization may include typed scope bounds and explicit adjustment kinds; an exact file list remains restrictive when specified. Reuse the same whole-plan approval across its named Tasks. Each Attempt still records exact operations, files and worktree version. Platform permission remains independently required.
2. Within the approved boundary, continue across Task and record transitions without repeated confirmation. Record reasons and precise versions before adding files, narrowing tests, diagnosis or same-cause correction; inspect actual content and revalidate dependencies/conflicts before writing. Source, lock, fingerprint and recovery checks remain mandatory. A known retry may reuse its recorded scope authorization; an uncertain result may not be rerun.
3. Stop for expanded goals, modules, modification types, risks, external effects, changed public behavior or impacts on other Task arrangements. Explicit exact-file limits and revoked scope remain binding. Unknown results and drift stay blocked; no command text analyzer or host permission bypass substitutes for review. Safe current-write reversal is handled only by the complete-change recovery rules.
4. When execution discovers an insufficiency, submit `work-execution-deviation-semantic-request` to `execute deviation-prepare-semantic` while the affected record remains reserved, except for file-only registration on the idle Attempt. Describe the gap, semantic action, supplemental file scope, semantic impact and side effects. For example, `{"kind":"replace_command","replacement":{"mode":"argv","argv":["tool","test"]}}` contains no record ID. Use one-based `command_positions`, `validation_position`, `command_position` and `acceptance_positions` to refer to existing items in the current TASK when adding a validation or adjusting an operation. Never supply formal IDs or direct ID references in the semantic action. The Work CLI derives the TASK, Attempt, reserved record and formal task basis from the active lock and TASK, allocates new command or validation IDs, resolves positions, and runs the existing full proposal validation. Review the returned complete proposal, action, semantic impact, side effects, classification, blocking flag, source fingerprints and `preview_sha256`; save its exact `proposal` for `deviation-record`. The old full-proposal preparation command is unsupported. For an explicitly permitted scope adjustment, retain a complete semantic impact review; unchanged boundaries may reuse original approval. Changed boundaries require a new decision.
5. Run execute deviation-record only after reviewing the exact preview. Inside a recorded scope that permits this adjustment and supplemental files, use the original approval evidence; otherwise obtain fresh approval. The existing deviation binds the preview, exact action, file list, impact review and evidence. Work does not extend module or explicit file boundaries merely because a path was listed. Drift requires a new preview.
6. For a recorded non-blocking deviation, keep the same Attempt and reserved record. `record-begin`, command preview and execution, and `record-finish` resolve the effective record, operation, command, authorization evidence and applicable file scope from the original Attempt plus that exact supplemental authorization. An approved `skip_record` finishes the reserved record only with canonical skipped evidence bound to the same record ID, reason and deviation ID; it ends that reservation without satisfying a necessary VAL. A later replacement of the same CMD must target its next instance after a known result; each historical receipt retains its applicable command. Duplicate submissions for the same instance, mismatched anchors, blocking actions and any unapproved record or file remain hard stops. For a recorded blocking deviation, do not revise TASK or Execution first: stop further execution, close the Attempt as a specification defect through the permitted blocking-close path, then enter reconciliation.
7. After close, begin review of unresolved deviations with `specification reconciliation-prepare`, supplying the closed Attempt path and confirmed semantic choice and edits. Save its CLI-prepared `data.request`, run `specification reconciliation-preview`, then bind approval to the complete reconciliation fingerprint and publish with `specification reconciliation-apply`. `retain_only` publishes only the ledger through a recoverable transaction; other choices publish the reviewed specification candidates and ledger together. The ledger records incorporated, retained and declined outcomes without rewriting the closed Attempt, and workflow routing excludes those resolved IDs. Recover an interrupted transaction only through its separately authorized recovery command.

8. To register files without changing CMD or VAL, use the same semantic deviation workflow on an idle Attempt with `action: {"kind":"add_files","modification_types":["create"]}` and the exact nonempty `modifiable_files`. Explain the gap and unchanged impact. The original scope must permit `additional_files` and the listed modification types, modules and exact-file restrictions. Preview and record check the full Task dependency graph and prior accepted file scopes. Record the exact reviewed proposal with `deviation-record`; success retains `lock_status: attempt_held`. Then read the complete current baseline and use `file-apply`. No artificial command adjustment, direct Attempt edit or record reservation is needed.
9. Every accepted additional VAL is part of the effective Task used by record execution, aggregation, close and recovery. Missing, skipped or failed additional VAL blocks completion. Adding the first CMD to a Task without defaults requires complete `execution` settings.
