# Recover one execution transaction

Project-file transactions use the separate publish-project-files.md: `file-recovery-prepare` inventories the full original/actual set, and freshly authorized `file-restore` restores the pre-transaction state. This does not change the forward direction of the record recovery below, and never reruns a CMD/OP.


1. Use `<work-cli> execute recover --input-file "<request-path>"` only after record-begin, command-correction, record-finish, attempt-close, or Correction reports `recovery_required: true` and the user separately authorizes recovery of the observed state. Attempt-start continues to use `recover-attempt-start`.
2. First use the read-only `<work-cli> execute recovery-prepare --input-file "<preparation-path>"` with the normal explicit TASK/execution paths, TASK ID and roots. Its schema is `work-execution-recovery-prepare-request`, with confirmed `transaction` (`record_begin`, `command_correction`, `record_finish`, `deviation_record`, `attempt_close` or `correction`) and `attempt_id`. It inventories the full domain staging transaction, manifest and actual payload/control files, checks formal identities and returns `data.request` containing `transaction_dir`, sorted `transaction_files` and `transaction_evidence_sha256`. Save only that request for authorized recovery. Preparation creates no writer mutex, target, journal or lock; legacy `.work-*.tmp` requests are unsupported.
3. Require `work-execution-recovery` with `status: recovered`. The command revalidates formal TASK identity, canonical Attempt, index, original lock fingerprint, mapped acceptance results and every prepared byte before advancing only the unique transaction. Record-finish and completed close recovery also recheck actual owned CMD receipts, structured VAL evidence and retained project publication; recovery cannot invent process success or rerun a command.
4. Any file-set change, byte mismatch, ambiguous state, unsupported attempt-start transaction, or write failure is a hard stop. Preserve all artifacts and locks; never retry automatically, roll back, delete a transaction file, rewrite a closed Attempt, or manually unlock.
5. Preparation is an inventory for review, not authorization or proof of a unique recovery target. Recovery reconstructs and verifies the domain targets after separate authorization; changed bytes, sizes, entries or partial/missing states invalidate its inventory digest and require new preparation. Preserve all process receipts and partial output outside transaction cleanup. External effects require independent review and are not restored by file isolation. Attempt-start keeps its original request and dedicated recovery procedure.
An authorized Attempt reuses the authorization manifest for matching commands,
validations, external operations, file changes, and allowed deviations. Retries,
recovery, failed or unknown results, and stopped or blocked closure require fresh
authorization evidence. Any scope expansion stops before the operation.
