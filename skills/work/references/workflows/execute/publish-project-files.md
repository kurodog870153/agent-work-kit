# Bind and record a complete Host project-file change

1. Read the current project paths and compose one complete simultaneous `changes` set. A `write` supplies final bytes. A `move` names an initial source and final destination, optionally with replacement bytes. Paths refer to the same initial tree; include an old-path replacement or a swap in the same set. Preserve user contents and earlier successful changes.
2. Before Host editing, call `execute file-binding` with `{"schema":"work-file-transaction-request","command":{"kind":"bind","attempt_id":"ATTEMPT-001","changes":[{"kind":"write","path":"target.txt","bytes":[10]}],"baseline_confirmation":null}}`. Work checks Task/Attempt scope, declared inputs, source and instruction fingerprints, dependency order, current path identities, bytes and metadata. It freezes the complete before/after candidate and Attempt authorization in a Work-owned prepared transaction. The returned `manifest.transaction_identity` and `manifest.approval_sha256` identify this exact set.
3. Host edits only the approved project paths. Host writes a project-local `work-host-file-evidence` JSON object with `task_id`, `attempt_id`, `transaction_identity`, `status`, `source_reference`, `atomicity_statement`, and `paths`. Each path has `before_sha256` and `after_sha256` matching the frozen manifest, using null for absence. `completed_atomic` is the Host's explicit claim about the whole set; Work cannot observe the edit sequence. Do not infer atomic completion from a successful tool call alone.
4. After editing, call `execute file-record` with `{"schema":"work-file-transaction-request","command":{"kind":"record","report":{"schema":"work-host-file-report","task_id":"TASK-001","attempt_id":"ATTEMPT-001","transaction_identity":"<binding identity>","approval_sha256":"<binding approval SHA>","result_origin":"host_reported","result_reference":"host-file-evidence.json","result_sha256":"<raw evidence SHA-256>","status":"completed_atomic"}}}`. Work rereads the raw evidence, checks all target bytes, metadata, identities, current Source/Attempt context and retained history, then publishes only formal file history. Work never applies or restores project source bytes through this command.
5. `partial`, `unknown`, missing targets, mismatched evidence, changed inputs or metadata, or a conflicting version remain incomplete. Preserve the actual files and prepared evidence. Do not retry an unknown edit or overwrite current contents to force a match. Resolve the actual state and authorization before any new action.
6. A new change after a published version uses a fresh `file-binding` on the currently observed tree. If the user changed a previously published path, inspect the complete baseline returned by `file_transaction_baseline_confirmation_required`; obtain explicit confirmation for that exact `previous_transaction`, `before_sha256` and evidence before binding again. This never authorizes an old unknown operation or expands scope.
7. Formal Source, TASK, Specification and Execution artifacts retain their Work-owned Lock, Journal, publication and Recovery rules. The retired `file-prepare`, `file-apply`, `file-recovery-prepare` and `file-restore` public commands cannot write project files. Historical file transactions remain readable and verifiable; do not remove their retained evidence.
8. Supported targets remain ordinary writable files with existing parents on the same filesystem. Link, reparse and hard-link aliases, portable path collisions, special files and unsupported metadata are rejected. Directory inputs are dependency ranges whose directory type is checked; file inputs retain byte fingerprints. Work does not reset to Git HEAD, clear tool outputs or handle credentials.
9. VAL and Acceptance use the current verified file-history version. A later change requires fresh validation. A failed test after a complete Host edit does not reverse the edit; preserve it for an authorized correction. Declared inputs follow moves in complete verified publications, including continuation ancestry.
