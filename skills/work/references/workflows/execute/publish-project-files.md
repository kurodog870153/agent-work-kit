# Apply or restore a complete project-file change

1. Read every affected current path and retain the SHA-256 of those exact bytes before composing one complete simultaneous change. `expected_before` must cover exactly every initial write path, move source and move destination; use null only for observed absence. Invoke `execute file-apply` with the normal task/execution paths, user-config-root and a `work-file-transaction-request`, for example a new file: `{"schema":"work-file-transaction-request","command":{"kind":"apply","attempt_id":"ATTEMPT-001","changes":[{"kind":"write","path":"target.txt","bytes":[10]}],"expected_before":{"target.txt":null}}`. A missing or stale baseline refuses the entire change. Never refresh hashes without rereading and reconciling the proposed contents. The active Attempt authorization covers the change; no caller-managed staging or separate publication approval is required. `file-prepare` accepts kind `prepare`, attempt_id, changes and optional baseline_confirmation for a preview; it does not replace the caller's original read baseline. Preparation can measure new-file metadata with an owned temporary probe but never edits formal targets.
2. A `write` describes final bytes. A `move` names its initial source and final destination, with optional replacement bytes. All paths refer to the same initial tree: move plus an old-path replacement or a swap must be expressed together. Each operation covers one complete change, and the same Attempt may apply further complete changes after testing. Extra files must stay within the recorded scope and pass DAG checks against declared files and all Tasks' retained accepted file scopes, including restored transactions. Work never invents dependency edges. Directory inputs are dependency ranges whose directory type is rechecked; individual file inputs retain byte fingerprints. Directory contents are not recursively snapshotted. Work preserves current bytes and supported metadata, including uncommitted contents and earlier successful changes; it does not reset to Git HEAD or clean tool outputs.
3. Work rechecks the complete current tree, native path identities, authorization, source evidence, resources and conflict order under writer ownership, persists the complete before/after candidate and predecessor identity, then applies and reads back the set. Unknown or incomplete evidence blocks writes and completion. No instantaneous multi-file filesystem swap or protection against arbitrary same-user writers is promised.
4. If a user changes a previously published path between operations, preserve it and inspect the complete `before` plus `path_identities` returned with `file_transaction_baseline_confirmation_required`. Obtain explicit confirmation of that exact baseline and include `baseline_confirmation` with its `previous_transaction`, `before_sha256` and actual confirmation `evidence` in the next direct request. The hash binds bytes, metadata, existence and physical identities. A different predecessor, changed baseline or empty evidence is refused. This confirmation never authorizes an old unknown transaction or expands the original scope.
5. The original scope can explicitly set `rollback_on_write_failure: true`. Only the same live invocation may then restore its known failed write, and only while the entire verified frontier, physical identities and authorization remain unchanged. The result is an error, `file_transaction_write_failed_restored`, with phase `restored`; it is not successful publication. Earlier successful transactions and confirmed user contents remain intact. Absent or false permission grants no automatic restore. A completed write followed by a failing test is retained for the next complete correction.
6. Crashes, unknown results, extra changes, corrupt evidence and failed restoration preserve current contents and runtime evidence and block affected work. Never rerun an unknown CMD. For explicit recovery, invoke `file-recovery-prepare` with kind `recovery-prepare` and transaction_identity; obtain fresh authorization for that exact preview, then use `file-restore` with kind `restore`, transaction_identity, approval_sha256 as approved_sha256 and fresh authorization_evidence. Recovery restores only that transaction's before, never the entire history. It does not acquire retroactive automatic-rollback permission. Existing execution record recovery retains its forward direction.
7. Supported targets are ordinary writable files with existing parents on the same filesystem. Link/reparse/hard-link aliases, portable collisions, special/readonly files and unsupported metadata are rejected before target changes. Windows preserves supported owner/group/DACL and inheritance protection and rejects named streams. macOS preserves owner/group/mode and supported binary extended attributes; unsupported ACLs and unverifiable metadata refuse the full preflight. New-file metadata is measured from an actual same-parent preparation probe. Timestamps and Windows audit SACLs are outside the contract. Never stage credentials.
8. CMDs execute in the inherited host environment and retain actual owned receipts. Current automated validation must reference the current file-history version; historical generation receipts remain historical evidence and cannot validate a newer version. All non-skipped VAL records bind their producer-verified file version, and later changes or confirmed baselines require fresh validation before completion. Closure and closure recovery recheck retained ordered publication and execution evidence. External OP keeps its own authorization and side-effect evidence; local restoration does not undo remote effects.
9. Declared inputs follow moves recorded by complete verified publications, including verified continuation ancestry. Further changes and command acceptance fingerprint the current destination bytes; do not recreate an old input path or use its original bytes as current evidence. Each publication resolves all moves against its own initial tree. Missing paths without verified history still block file preparation.
10. Requirement provenance and planning review are separate. Use the Task's actual Discussion trace where present; a reconstruction without that trace must bind its real completed Migration approval, original evidence and exact published candidates. Reconstruction may preserve a valid Snapshot source. It does not require a fabricated Discussion or a rewritten migration source, and it does not grant Execute permission.
