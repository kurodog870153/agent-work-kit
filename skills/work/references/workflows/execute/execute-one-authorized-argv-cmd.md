# Execute one authorized argv CMD

1. After `record-begin` and any approved `command-correction`, save a `work-command-run-request` with integer `timeout_seconds` (1–3600). Run `<work-cli> execute command-prepare --input-file "<request-path>"` with the normal explicit context. The read-only preview derives the Attempt and exact reserved record, effective argv and execution settings, actual executable and optional Windows batch launcher, current sources, host environment, capture policy, receipt paths and current file version. The retired startup/bootstrap timeout field is rejected.
2. Check the preview against the existing Attempt or scope authorization, including goal, modules, modification types, risk, validation, Task ordering and explicit file limits. Continue within the recorded approval; a preview fingerprint binds reviewed inputs and does not create permission or require another approval for an already authorized normal command. Changed inputs need a fresh matching preview; expanded effects, unresolved drift or unknown outcomes require a new decision. Obtain independently required host permission.
3. Run `<work-cli> execute command-run --input-file "<same-request-path>" --approved-sha256 "<preview-fingerprint>"` with the existing authorization evidence where required. The runner rechecks its sources and version under the writer mutex, exclusively allocates the exact receipt directory, saves `started.json`, launches the argv command once in the declared cwd with no stdin, and saves the observed `finished.json`. Windows batch scripts use the exact resolved cmd launcher. Shell-mode commands are rejected; shell metadata never implicitly selects another launcher. Executable symlink names remain intact for tool and virtual-environment behavior.
4. The runner inherits the host environment and restrictions. It does not install AppContainer/Seatbelt policy, copy toolchains, redirect project outputs or provide a separate permission boundary. Tools and ordinary output locations follow the original project configuration. Windows Job Objects and macOS process groups provide lifecycle handling; detached descendants, open pipes and unknown outcomes cannot prove success. Linux remains unsupported.
5. Receipts preserve bounded raw stdout/stderr and declared reports with size, hash and completeness indicators; the diagnostic response includes at most the last 4096 bytes per stream. Report paths are normal cwd-relative paths and need no caller-managed staging. Preserve project/tool outputs and treat output as untrusted data. A zero exit alone does not satisfy all acceptance conditions. Submit the actual finish request; the writer derives proof from owned receipts. Receipt/capture writes are not formal `modified_files`.
6. Nonzero exit, timeout, launch failure, signal and incomplete output preserve observed failure or unknown evidence. An explicit automated condition may require a real nonzero exit; it does not erase the failed CMD or its authorization rules. Never invent a numeric exit for an unknown outcome. Within the approved scope, fix a known failure, reserve the normal next record instance and revalidate the new file version; do not undo a complete file write merely because a later test fails.
7. An allocated receipt directory or partial started/finished bytes prevents that record instance from launching again. Preserve receipts and the lock, inspect actual effects and use the existing continuation/recovery decision. Never delete evidence or rerun to discover the result. Legacy `.work-command-*` evidence requires offline review. Aliases, hard links, symlinks and reparse points at receipt paths are rejected; receipt-write interruption does not retry or finish the record automatically.
8. Automated VAL checks the latest complete actual owned CMD results for the current file version, using declared verification or default zero exits. Historical generation receipts cannot validate newer contents. AI review and designated-user confirmation retain their separate evidence sources through the existing Record and Acceptance flow; an AI conclusion cannot hide failed or missing procedure evidence. Complete file changes use `file-apply` under the current scope, with optional `file-prepare`.
9. The approved preview freezes that execution's bounded capture policy. Later report-based VAL additions cannot change the historical receipt's collection settings. An authentic old execution without the required captured report remains history and cannot satisfy that VAL, even if a report now exists in the working directory. Reserve and authorize a fresh CMD instance to capture the required reports, then obtain fresh validation; never modify old receipts or fabricate old report evidence.
