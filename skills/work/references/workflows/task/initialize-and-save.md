# Initialize and save

1. Obtain one bounded Session save authorization for the explicit requirement, canonical project root, exact discussions directory, allowed actions and evidence. Preserve the fixed Source and independently confirmed Task hierarchy, skills and main acceptance in `context.confirmed_source`; this may remain null while choices are still being discussed. No formal candidate is required to retain unresolved context.
2. Use `discussion init` with a strict `work-discussion-request` containing the complete validated initial Session. All integrity derivation belongs to the deterministic Work implementation. Initialization verifies revision 1, authorization and content integrity, writes immutable history, then commits current and reads it back. Do not manually repair metadata or historical bytes.
3. Use `discussion update` with one local operation containing a unique `operation_id`, exact `expected_revision`, `previous_sha256` and typed change. Add/update a decision, update one planning record, update requirement context or continuation. Preserve omitted unrelated records. New decisions use the next stable D ID and record why the question was added; TASK IDs are stable and never reused.
4. Decisions retain question/options, tentative choice, explicit state/reason/evidence, confirmed resolution/rationale, TASK links and dependencies. Plans retain direct executable domain records and review evidence; no complete persisted formal candidate is a second authority. Changed upstream decisions/context invalidate affected reviews and dependent confirmed decisions.
5. Use `discussion question` to save the exact text/version/number-to-option mapping, then ask only from verified returned data. Use `discussion answer` with decision identity, question version, displayed number, rationale and confirmation evidence. Each request kind must match the invoked command.
6. Verify returned revision, content SHA and minimal view after every successful save. Identical operation retries do not add revisions, even after later commits; the same operation ID with different content is rejected. Save authorization remains separate from full formal preview approval and execution authorization.
7. Review each Task for one verifiable outcome; split independently acceptable outcomes and retain a concrete rationale for inseparable multi-file changes in the existing semantic consistency evidence. Work validates required planning structure and review freshness, rather than a second outcome mapping or transaction feasibility declaration. Ask one question at a time when the outcome cannot be determined; never use file, line or step counts as a splitting threshold.
