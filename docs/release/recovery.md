# Work 安裝交易與復原

## 1. 交易身分與執行順序

Source 和 Package 安裝器在 Windows、macOS 使用相同的交易模型。平台安裝鎖序列化正式目標與交易紀錄的檢查和修改。新一輪設定選擇前，安裝器先檢查對應目標的殘留 Global AGENTS 與 Work 交易；`--dry-run` 不改動待復原交易，遇到它們時停止。

對於正式 Work 路徑 `<parent>/work`，安裝器在同層建立私有 `.work-install.<random>` 目錄。`prepared/` 保存待發布的新 Work；舊 Work 需要移開時放入 `previous/`。交易資料記錄正式目標，以及待發布狀態與 binary 的 SHA-256。完成標記只在正式路徑通過驗證後寫入。不能僅憑 `.work-install.*` 目錄名稱判定它屬於安裝器。

## 2. 發布與完成

1. 核對目標路徑、既有內容、首次更新確認、版本與 Work binary 使用狀態。
2. 建立 `prepared/`，放入選定 Skill、binary 及有效的 `install-state.json`；驗證完整內容和 binary 啟動。
3. 在第一次切換前再次預檢正式目標，然後將既有安全 Work 移到 `previous/`。
4. 將 `prepared/` 移至正式路徑，重新驗證正式 Work；成功後記錄已驗證完成。
5. 再次確認舊版與交易目錄的身分，安全清理。若清理受阻，已驗證的新 Work 保持生效，安裝回報成功並保留待清理路徑。

發布前失敗時，正式目標維持原狀。切換或正式驗證失敗時，安裝器嘗試恢復 `previous/`；若無法證明恢復安全，保留新舊內容和交易紀錄並停止，不宣告成功。

## 3. 中斷後的判定

重新執行時，安裝器持鎖核對交易所記錄的目標與內容身分。正式目錄若沒有完成標記，即使檔案看似完整，仍是未驗證版本。

| 可確認的狀態 | 復原方向 |
| --- | --- |
| 只有 `prepared/`，舊 Work 仍在正式路徑 | 清除已確認屬於交易的不完整 staging，再重新安裝 |
| 有 `previous/`，正式路徑沒有 Work | 暫時移回已驗證的舊 Work 保護資料，接著重新安裝新版 |
| 有 `previous/` 和未驗證的新 Work | 核對新 Work 身分，移走半成品並保護舊 Work，接著重新安裝新版 |
| 有完成標記且正式新 Work 與紀錄相符 | 保留新版，只重試安全清理舊版與交易資料 |
| 首次安裝留下未驗證的新 Work，沒有 `previous/` | 僅在紀錄與內容均能證明所有權時清除半成品並重新安裝 |

恢復舊版只是重新安裝前的資料保護措施，不代表新版安裝完成。多筆交易指向同一目標、紀錄損壞、未知內容、連結或檔案遭外部修改時，保留現場並要求人工檢查；不刪除未知資料，也不終止其他程序來取得鎖。

## 4. Global AGENTS 與 Work 的共同邊界

需要新增或取代 Global `AGENTS.md` 時，安裝器另建 `.agents-install.*` 交易目錄，記錄 Work 目標、Global AGENTS 目標、操作類型、新內容及原內容的雜湊。Global AGENTS 先進入交易，再發布 Work；Work 最終驗證後，兩者的關聯紀錄才標記已驗證並進行清理。

下次執行先檢查相符的 Global AGENTS 交易。若 Work 已完成且兩個正式目標的內容與紀錄相符，保留新版並重試清理。若 Work 未完成，僅在雜湊足以證明所有權時恢復原 Global AGENTS 內容或原本不存在的狀態，再處理 Work 並重新安裝。紀錄不明、目標遭修改或恢復失敗時保留資料並停止。未啟用或決定不修改 Global AGENTS 時，不建立這筆交易。

## 5. 路徑遷移的延後清理

從受管理的預設 Work 路徑遷移到新 `--work-install-dir` 時，安裝器在新目標同層保存 `.work-migration-cleanup` 紀錄，連結舊絕對路徑、新安裝狀態雜湊和舊目錄指紋。新 Work 成功發布後才嘗試刪除舊位置。

若舊 Work 因使用中、鎖定或內容變更而不能安全清理，安裝器保留舊目錄及紀錄。下次執行須重新核對紀錄、新狀態、舊 Work 的受管理結構與內容指紋，以及 binary 是否仍在使用；無法確認時只顯示警告。未驗證的新目標不能因存在遷移紀錄而視為已完成。

狀態格式見[安裝狀態](install-state.md)；交易階段與中斷案例的完整契約見 [Issue #95 交易契約](../issue-95/transaction-contract.md)。
